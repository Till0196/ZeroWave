外部プロセスによる補間のバックエンド（`interpolate/process`）と本体の間のプロトコル。

プラグインが [`Process`](super::Process) で指定した実行ファイルを本体が起動し、前と今の二枚のフレームを
渡して中間フレームを受け取る。指定は設定のキーの名前で、起動できるのは `kind = "program"` のキーにユーザーが
入れたパスだけ。作業フォルダーと `PATH` に追加するものも `kind = "folder"` のキーが指すフォルダーに限る。内部の実装（TensorRT、CoreML、CPU…）はプロセスの自由で、クラッシュしても
影響はそのプロセスだけに留まる。参考実装は zerowave_plugins の `video-filter/zwtrt/`（zwtrt、
TensorRT、C++。メッセージの読み書きをする `protocol.h`・`protocol.cpp` はそのままコピーして使える）と
`video-filter/zwcoreml/`（zwcoreml、CoreML、Rust。このモジュールの [`Request`]・[`reply`] などで
読み書きする）。

ジョブ（中間フレーム一枚）は同時に複数投げられる。数は OPEN で決める（本体が出せる数を伝え、プロセスが
処理できる数を返す）。フレームは入力ごとに一度だけ渡す：入力スロットに入れた入力は、それを「今」にするジョブと
「前」にする次のジョブの両方が同じスロットを参照する。

# 転送方式

本体はメッセージを送り、プロセスは一つのメッセージに一つの応答を返す。OPEN と SHARE は本体が応答を
待ってから次を送る。RUN の応答は、フェンス方式では受け取った順、メッセージ方式では書き終えた順でよい
（応答に値が入る）。

- **Windows**：標準入力（本体 → プロセス）と標準出力（プロセス → 本体）はそれぞれパイプ。
- **Linux・macOS**：標準入力と標準出力は**同じ一本の unix ソケット**（`SOCK_STREAM`、双方向）。
  fd を渡す SHARE には、そのメッセージのバイトに `SCM_RIGHTS` で fd が一つ付く。受信側は
  常に `recvmsg` で読み、付いてきた fd を受け取った順にキューに入れておき、fd が必要な SHARE で一つ取り出す
  （`read` で読むと付いてきた fd は破棄される）。
- 標準エラーは本体のログへ送られる。`@status <割合> <テキスト>` の行（割合は `0`〜`1`、不明なら `-`）は
  準備（OPEN）の進捗で、本体はプラグインへ「準備しています」の通知として渡す。
- 標準出力にメッセージ以外を書かない（ライブラリーが printf するなら、メッセージ用の fd を複製してから標準出力を
  標準エラーへリダイレクトする）。

## 形式（little endian）

```text
本体 → プロセス：{op u32, 長さ u32, 中身[長さ]}
プロセス → 本体：{状態 i32, 長さ u32, 中身[長さ]}
```

状態が 0 でなければ失敗で、中身は理由の UTF-8（本体はログとプラグインへの通知に出す）。
失敗の応答を返したあとも、プロセスは次のメッセージを待つ。

## 終了

標準入力が閉じたら（EOF）、インポートしたリソースを解放して終了する。本体は接続を閉じてから 2 秒待ち、
残っていれば強制終了する。本体がクラッシュしたときは：

- Windows：本体は子プロセスをジョブオブジェクト（閉じたら中のプロセスを終了する）に入れる。
- Linux：本体は子プロセスに `PR_SET_PDEATHSIG`（`SIGKILL`）を付けて起動する。
- macOS：同等の仕組みが無い。準備に時間がかかるなら、その間も親の終了（`kqueue` の
  `EVFILT_PROC`・`NOTE_EXIT`、または `getppid()` の変化）を別スレッドで監視して、終了すること。

# メッセージ

## 1 OPEN（準備）

```text
{幅 u32, 高さ u32, 同時実行数 u32,
 方式の数 u32, 方式[方式の数] = {方式 u32, 長さ u32, 中身[長さ]},
 形式の数 u32, 形式 u32[形式の数]}
→ {方式 u32, 形式 u32, 同時実行数 u32}
```

本体が対応する転送方式（優先順）とフレームの形式を並べ、プロセスがそれぞれ一つ選んで返す。
使えるものが無ければ失敗を返す。準備（エンジンの構築、モデルの読み込みなど）はこの間に行ってよく、
数分かかってもよい（本体はその間、補間せずに再生を続ける）。初回の推論が遅いなら、ここで一度実行しておく。
OPEN はプロセスの生存中に一度だけ来る（サイズが変われば、本体は新しいプロセスを起動する）。

同時実行数は、完了していないジョブを同時にいくつまで抱えるか。本体は自分が出せる数（1 以上）を伝え、
プロセスは 1 からその数までの範囲で、選んだ方式で自分が処理できる数を返す（一つずつしか処理できなければ 1。
GPU のキューに順に積むだけでも、転送と推論が重なるので 2 が有効）。

方式（中身はレンダリングに使う GPU を識別する情報。プロセスは自分が使う GPU と同じかを確認する）：

| 方式 | 名前 | 中身 | 同期 |
|---|---|---|---|
| 1 | `d3d12` | アダプターの LUID（8 バイト：LowPart u32、HighPart i32） | フェンス |
| 2 | `vulkan` | `deviceUUID`（16 バイト）と `driverUUID`（16 バイト） | フェンス |
| 3 | `metal` | `registryID` u64 と、mach のサービス名（残り全部、UTF-8） | メッセージ |
| 4 | `shm` | 無し | メッセージ |

形式：1 は f32、2 は f16（IEEE 754 の半精度）。

## 2 SHARE（共有リソースの受け渡し）

```text
{種類 u32, 番号 u32, 行の幅 u32, サイズ u64, ハンドル u64} → {}
```

OPEN の応答のあと、本体は次のリソースを、この順で一つずつ渡す（同時実行数を n として）。

| 種類 | 名前 | 数 | 中身 |
|---|---|---|---|
| 0 | 入力 | n + 1（番号 0〜n） | 前か今にする入力フレームのスロット |
| 1 | 中間 | n（番号 0〜n − 1） | 中間フレームを書くスロット |
| 2 | ready | 1（フェンス方式だけ） | 本体がシグナルし、プロセスが待つ |
| 3 | done | 1（フェンス方式だけ） | プロセスがシグナルし、本体が確認する |

行の幅（バイト）はフレームのもの、フェンスでは 0。番号はフェンスなら 0。サイズは割り当てのサイズ
（インポート時に指定するもの）。

| 方式 | フレーム | フェンス | ハンドル |
|---|---|---|---|
| `d3d12` | 共有ヒープのバッファ（`ID3D12Resource`） | 共有フェンス（`ID3D12Fence`） | 本体がプロセスへ複製した NT ハンドル。インポートしたら閉じる |
| `vulkan` | エクスポートしたメモリ（専用の割り当て） | タイムラインセマフォ | 0。fd（`OPAQUE_FD`）がこのメッセージに付く |
| `metal` | `IOSurface` | 無し | 0。IOSurface の mach ポートが先に mach のメッセージで来る（下） |
| `shm` | 共有メモリ | 無し | Windows は複製したファイルマッピングのハンドル、Unix は 0 で fd が付く |

`metal`：プロセスは OPEN の応答を返す**前に** `bootstrap_check_in(bootstrap_port, 名前)` で
受信ポートを作っておく。本体は SHARE を送る前に、そのポートへ `msgh_id` が
「種類 × 256 + 番号」のメッセージ（複合メッセージ、ポート記述子が一つ：`IOSurfaceCreateMachPort` の
送信権）を送る。プロセスは SHARE を受けたら `mach_msg` で一つ受信し、`IOSurfaceLookupFromMachPort`
で開く。

`shm`：サイズ分を読み書き可能でマップする（Windows は `MapViewOfFile`、Unix は `mmap` の `MAP_SHARED`）。

## 3 RUN（一枚生成）

```text
{値 u64, 位相 f32, 前 u32, 今 u32, 中間 u32}
→ {値 u64, GPU の時間 f32（ミリ秒、不明なら負）}
```

入力スロット「前」と「今」から位相（0 が前、1 が今。現在は 0.5 だけ）のフレームを生成して、中間スロット「中間」へ
書く。値は 1 から一つずつ増える。応答の値は RUN の値。

本体の規則：

- 完了していないジョブが同時実行数を超えないように送る（完了とは、フェンス方式は done がその値に達した、
  メッセージ方式は応答が来た）。
- 完了していないジョブが読む入力スロットと書く中間スロットには触らない。新しい入力は空いたスロットへ入れる。
  二つのジョブが同じ入力スロットを読むことはある（ある入力が一つのジョブの「今」で、次のジョブの「前」）。

方式ごとの同期：

- **フェンス方式**（`d3d12`・`vulkan`）：本体は入力を書き終えたら ready を RUN の値にする（値の順に）。
  プロセスは ready がその値に達するのを GPU 上で待ってから読み、書き終えたら done をその値にする。done は
  **値の順に**進める（done が v なら v までのジョブが全部完了した。並行して処理するなら、先の値のジョブが
  完了するまで後の値を進めない。一本のキューに順に積めばそうなる）。応答はキューに積んだらすぐ、受け取った順に
  返す（完了を待たない。時間は分かっている最新の完了したジョブのもの）。
- **メッセージ方式**（`metal`・`shm`）：RUN が来た時点で前と今は書き終わっている。中間を書き終えてから
  応答を返す（応答が done の代わり。完了した順でよい）。時間はこのジョブのもの。`metal` で CPU から
  アクセスするなら `IOSurfaceLock`・`Unlock` で挟む。

失敗の応答（状態が 0 でない）を受けたら、本体はそのバックエンドの使用をやめる。

# フレーム

RGB の三つのプレーンを縦に並べたもの。プレーン c（0 赤、1 緑、2 青）の y 行目は、先頭から `(c × 高さ + y) × 行の幅`
バイトの位置に、幅の数だけ値が並ぶ。値は 0〜1（レンダリング側の色のまま、ガンマも掛けたまま）。
行の幅は SHARE で指定されたものを使う（幅 × 値のバイト数より広いことがある。余りの部分の値は使わない）。

- `d3d12`・`vulkan`・`shm`：行の幅は `幅 × 値のバイト数` を 4 の倍数へ切り上げたもの
  （f32 ならパディング無し）。三つのプレーンは連続している。
- `metal`：IOSurface は幅 × (3 × 高さ) の 1 成分の画像（f32 は `kCVPixelFormatType_OneComponent32Float`、
  f16 は `kCVPixelFormatType_OneComponent16Half`）で、行の幅は IOSurface の `bytesPerRow`。CoreML なら
  `CVPixelBufferCreateWithIOSurface` でラップして、`MLMultiArray(pixelBuffer:shape:)` の [1, 3, 高さ, 幅]
  で渡せる。

# 本体側の方式の選び方

本体はレンダリングに使う GPU の API で使える方式を先に、`shm` を最後に並べる（`shm` は本体が GPU から読み戻して
書き込むので遅いが、どこでも動く）。プラグインは [`Process::ways`](super::Process::ways) で並べる方式を
絞り込める（`//!WAY shm` など、試験用に）。

本体が伝える同時実行数は 2（[`JOBS`]）。メッセージ方式で、入力の転送が GPU で完了するのを待って RUN を
送る処理と、応答の受信はレンダリングのループとは別のスレッドで行い（レンダリングのループは完了したかを確認するだけ）、往復にレンダリングのループの
間隔の粗さが乗らないようにしている。
